# Security and Compliance

v1 has no user accounts, no payments and no personal data beyond public athlete names, so the attack surface is small. The rules below keep it that way, and define what must change if authentication is ever added.

## 1. Secrets
- Real values only in `.env` (gitignored). `.env.example` lists variable names with dummy values.
- GitHub Actions secrets for CI and scheduled runs.
- Add a pre-commit secret scan (for example `gitleaks`) and run it in CI.
- If a secret is ever committed, rotate it immediately. Deleting the commit is not enough.
- Logs must never contain secrets or full request headers.

## 2. Outbound access (scraping ethics and legality)
- Check and record `robots.txt` and terms of use per source (Phase 0).
- Honest `User-Agent` with contact information.
- Rate limit, cache, back off, stop on 403 or 429.
- Do not bypass logins, paywalls, CAPTCHAs or other access controls.
- Store facts (results) with source links. Do not republish full copyrighted pages, images or articles. Quoting short factual values is fine.
- If a source forbids automation, use manual import. Do not work around it.

## 3. Input handling
- All external data is untrusted. Parse defensively, validate with pydantic, never use `eval`, never execute fetched content.
- SQL is always parametrised (SQLAlchemy). No string-built queries.
- File paths for raw storage are generated by code from safe components, never from remote strings.
- Manual CSV import validates headers, types and sizes.
- Playwright (if used) runs without access to local credentials and only on allow-listed domains.

## 4. Dependencies
- Pin versions (lock file). Run `pip-audit` in CI. Update on a schedule.
- New dependencies need justification in the PR (see `AGENTS.md`).

## 5. Dashboard
- Read-only. No write paths, no file upload, no SQL input box.
- If hosted publicly, expose only aggregated and sourced facts. The database file with operational tables (runs, quarantine) stays private.
- No secrets in front-end code or in the repository.

## 6. LLM layer (optional)
- API key in environment variables only.
- Send only computed aggregate tables. No raw scraped text as instructions (prompt injection risk: scraped pages may contain hostile text).
- Output is labelled as generated. Numbers are verified against the computed tables before display; mismatch means discard the text.

## 7. If authentication is added later (not v1)
Treat as a design change with a decision record, and then:
- Passwords hashed with Argon2id (bcrypt acceptable). Never stored or logged in plain text.
- Separate authentication (who you are) from authorization (what you may do); roles such as Admin, Analyst, Viewer, enforced on the server for every request.
- Secure session or token handling: expiry, HTTP-only and secure cookies, CSRF protection where cookies are used, refresh and revocation strategy.
- Rate limiting and lockout on login, HTTPS only, audit log of sensitive actions.
- Security tests: unauthenticated access, wrong role, expired token, injection attempts.

## 8. Backups and integrity
- Raw store plus migrations plus reference CSVs are enough to rebuild the database. Keep copies of `data/raw/` and `data/reference/` outside the working machine (for example a private repository or cloud drive).
- Test a restore once per phase.
- Database dumps are never stored or uploaded in the clear. `sie backup --require-encryption` encrypts with `age` to a public recipient (`BACKUP_AGE_RECIPIENT`); the private identity lives only in the `BACKUP_AGE_IDENTITY` secret and an offline copy, never in the repository, logs or artifacts. The repository is public, so artifacts are world-readable by signed-in users: only `*.dump.age` and manifests may be uploaded (enforced by a guard step). Restore tests run in a scratch database and are refused against `DATABASE_URL`. Runbook: `DEPLOYMENT.md` section 3a, ADR-034.
